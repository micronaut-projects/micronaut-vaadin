Vaadin's development mode adds the development tools to the page, reloads the browser when the frontend changes, and builds the frontend on the fly when the application needs it. It starts when Vaadin's development server is on the classpath and production mode is off.

Add it for development only. With Gradle:

[source,groovy]
----
dependencies {
    developmentOnly("com.vaadin:vaadin-dev")
}
----

With Maven, add `com.vaadin:vaadin-dev` in a profile that production builds leave out.

While the application uses only Vaadin's own components, Vaadin serves its pre-built development bundle and no Node.js installation is needed. Custom frontend code, themes or add-ons with frontend dependencies make Vaadin build the bundle, which needs Node.js.

Vaadin starts development mode with the views and other Vaadin types known at compile time, so it finds the frontend dependencies of the application without scanning the classpath.

=== Live updates of the frontend

With `vaadin.frontend.hotdeploy` set to `true`, Vaadin runs Vite, and the browser receives the changes of the frontend sources as they are made. The Netty server proxies the browser's WebSocket to Vite on the port of the application, as a servlet container does, so that it works when the browser does not run on the same machine as Vite, such as with a development container.

=== Project folders

Development mode reads the frontend sources of the project and writes generated files into it. Vaadin's Gradle and Maven plugins tell it where the project and its build folder are. Without them, set the folders in the configuration:

[configuration]
----
vaadin:
  project:
    basedir: /path/to/project
  build:
    folder: build
----

`vaadin.build.folder` defaults to Maven's `target`.

=== Production mode

Set `vaadin.production-mode` to `true`, or build with the production profile of Vaadin's plugin, which also builds the production frontend bundle. Leave `com.vaadin:vaadin-dev` out of production builds.

=== Micronaut's development mode

Micronaut's development mode (`micronaut-dev`) recompiles the application as its sources change, and applies each change in place or restarts the application with a new generation of its classes. Add Micronaut Vaadin's development module next to Vaadin's, for development only:

dependency:io.micronaut.vaadin:micronaut-vaadin-dev[scope="developmentOnly"]

WARNING: Micronaut's development mode is experimental and is not released yet: `micronaut-vaadin-dev` builds against its branch of Micronaut core.

Each change is handled as follows:

* An edit of method bodies is applied in place, without a restart, when the development agent is attached. Vaadin's own hotswap then clears its caches of the changed classes and refreshes the views that use them: the session and the state of the UI are kept.
* An edit of the translations under `vaadin-i18n` reaches the running application without a restart.
* Any other change, such as a new view or a changed constructor, restarts the application. Vaadin starts again with the views of the new generation. A restart ends the Vaadin sessions: the browser reloads the page quietly instead of reporting that the session expired. Set `vaadin.dev.quiet-restart` to `false` to keep Vaadin's notification. An application that sets its own system messages keeps them.
* Frontend sources, under `src/main/frontend`, stay with Vaadin's development server.

To keep the Vaadin sessions, with their UIs, across a restart, enable Vaadin's session serialization for development mode:

[configuration]
----
vaadin:
  devmode:
    session-serialization:
      enabled: true
----

The stopping generation serializes the HTTP sessions, and the next one reads them back with its own classes: the browser keeps its session, and the views their state. Only serializable state carries over. A view that holds a bean which is not serializable, for example, is left behind, and the page reloads as without the option. This applies to the Netty server with Micronaut Session's in-memory store.

Prefer the Netty server for the development loop: during a restart it keeps its port and holds the requests that arrive until the new generation serves them.
