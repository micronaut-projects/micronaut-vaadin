Micronaut Vaadin runs on Micronaut's default Netty server, with no servlet container. Add the Netty integration:

dependency:io.micronaut.vaadin:micronaut-vaadin-netty[]

Vaadin's requests are served by functional routes, on the blocking executor: Vaadin holds the lock of a user's session while it runs application code, which must never block an event loop. Vaadin itself is written against the servlet API, so the integration gives it a request, a response and a servlet context of its own, backed by Micronaut.

=== URL mapping

`vaadin.url-mapping` and `vaadin.exclude-urls` work as on a servlet container. With the default `/*`, Vaadin serves the root of the application next to your controllers: any other route that matches a request wins, such as the routes of your controllers or the login endpoint of Micronaut Security, and the paths of static resources and of `vaadin.exclude-urls` stay with Micronaut.

Micronaut filters, including those of Micronaut Security, apply to Vaadin's requests like to any other route.

=== Sessions

Vaadin keeps its state in a session of https://micronaut-projects.github.io/micronaut-session/latest/guide/[Micronaut Session], which the integration brings in. The session is tracked with Micronaut Session's cookie, named `SESSION` by default. A Vaadin session holds the components of the user interface, so keep the sessions in memory and use sticky sessions when the application has several instances.

=== Push

Push runs over Micronaut's WebSocket support, which the integration brings in, at `/VAADIN/push` or below the prefix of `vaadin.url-mapping`. The live reload of Vaadin's development tools uses the same endpoint. Each connection's messages are handed to Vaadin one at a time, in order, on the blocking executor.

=== Uploads

The parts of an upload are written to temporary files before Vaadin handles the request, and deleted once the response is sent. `micronaut.server.max-request-size` limits the size of an upload, besides the limits of Vaadin's `Upload` component.
